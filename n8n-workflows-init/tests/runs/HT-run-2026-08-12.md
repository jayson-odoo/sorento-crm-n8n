# HT (human-intervened-timeout) — test run 2026-08-12

Tester pass against the S1/S2/S3 build artifacts (all inactive, per
`tests/manifests/human-intervened-timeout/README.md`). Target n8n:
`automate-sorento.foundryx.my`. Redis namespace used: `test:ht:*` /
`test:egress:HT-*` only — canonical `ht:*` was never touched (verified below).

**Headline finding: the sweeper's core "clear + notify" mechanism is dead on
arrival.** `ht-recheck-stamp`'s key expression reads `{{ $json.contact_id }}`,
but its real upstream node (`ht-findcontact`) never emits a `contact_id` field
(only `id`). Every expired candidate therefore recheck-reads a non-existent
key (`test:ht:active:` with an empty suffix), gets `ht_recheck_ms: null`, and
`ht-classify` unconditionally reports `skip-vanished` — **regardless of the
real flag value or real stamp state.** `clear-and-notify` and `forget-silent`
are structurally unreachable in a live execution. This is safe (fails toward
"do nothing"), but it means the feature does not do its job: flags are never
cleared, timeout notices are never sent, and `test:ht:active:*` keys are never
removed. See **Finding F-RECHECK** below; reproduced 4 independent times
against the real graph (2 via MCP manual mode, 2 via the real webhook with
proper `test_run_id` attribution).

## Summary of failures/anomalies for the reviewer

1. **F-RECHECK (blocking, functional, not a safety violation).**
   `ht-sweeper BUILD` → `ht-recheck-stamp` node, parameter
   `key: "=test:ht:active:{{ $json.contact_id }}"`. Its actual input
   (`ht-findcontact`'s output) has no `contact_id` field — only `id` — so the
   expression always resolves to `test:ht:active:` (empty suffix), always
   misses, and `ht-classify` always reports `skip-vanished` for every
   candidate, regardless of the real stamp or flag state. **Consequence:
   `clear-and-notify` and `forget-silent` are both unreachable; the flag is
   never cleared, the timeout notice is never sent, and `test:ht:active:*`
   keys accumulate forever.** Reproduced 4 times (executions 12170257,
   12170544, 12170937, 12171009), including 2 via the real webhook with
   correct `test_run_id` attribution and both `flag=true` and `flag=false`
   fixtures — same result both times, confirming the defect is independent of
   the fixture and purely a wiring/expression bug. This blocks HT-7 (partial),
   HT-8 (fail), HT-9 (fail), HT-16 (unreachable, not just untested), HT-17
   (unreachable, not just untested). Fix direction (for the coder, NOT applied
   by me): point the key expression at a field that actually carries the
   contact id at that position in the graph — either `{{ $json.id }}` (reading
   `ht-findcontact`'s real shape) or `{{ $('ht-sweep-fanout').item.json.contact_id }}`
   (matching the by-name-read pattern used everywhere else in this feature,
   per the build's own stated F7 rule). This is the exact §63/§71
   "wrong-object read on a workflow PARAMETER, not a Code body" class the
   manifest's own F7 finding warns about — it recurred one hop upstream of
   where the build fixed it in `ht-classify.js`, on a REDIS NODE PARAMETER the
   offline Code-body harness cannot see (confirmed: `harness.js`/`mutate.sh`
   construct `ht-recheck-stamp`'s output by hand, bypassing the real key
   expression entirely — this is why 133/133 offline assertions and 20/20
   mutants passed despite the defect).
2. **Residual test keys not cleanable** (see Cleanup section) — a direct
   downstream consequence of #1, not a separate defect.
2b. One incidental `Schedule Trigger` tick fired during the ~1s S2 activation
   window for HT-9 (execution 12171008) — harmless (same F-RECHECK-safe path),
   noted for completeness.
3. **HT-15 nuance**: literal timeout=0 takes the "reject→default 300s" branch
   of `ht-config-apply.js`, not the "clamp-to-60s-floor" branch — both are
   sanctioned by the case wording ("rejected / clamped to 60"), but a reviewer
   should know which branch a literal 0 actually exercises live (verified
   here) versus which branch the offline suite separately covers (0.5 min).
4. No new token sinks observed; no LLM node anywhere in these three
   workflows; get-results liveness is not applicable to this feature.
5. HT-FP1–FP4 were verified via the independently-rerun offline mutation
   battery (not re-driven live) — see the Fail-on-purpose section for the
   rationale and the specific `CAUGHT[...]` lines that cover each.

**Recommendation (original pass): REQUEST-CHANGES.** The trigger-side (S1) and config-form
(S3) slices are solid — 14 of 15 directly-live-testable cases pass cleanly,
and the one exception (HT-7) fails only on a precondition the sweeper cannot

fixed before this feature can do anything beyond stamping and notifying on
